# Origami Tutorial Generator — Implementation Plan

Source requirement: `.kunsdd/requirements/3ff39ad9-2f21-4493-9450-e73b3efd160a/requirement.md` (final draft, no images referenced).

## Summary

Build a personal web application that takes one photo of a single object and produces a human-followable origami folding tutorial. Pipeline: **photo → limb tree → box-pleated crease pattern (FOLD) → foldable simulation → folding history → illustrated tutorial**. Target audience: general public with no origami expertise. No commercial features; no model training from scratch.

### Carried-over scope decisions (from the draft)

- **Platform**: browser-based simulator + Python backend (FastAPI). Easy to share, no installs.
- **Input**: one photo, single roughly centered object, longest side ≥ 512 px; clean backgrounds preferred; violations are rejected with an explanation.
- **Data**: reuse pretrained vision models (segmentation + skeleton extraction); build only post-processing and limb-tree extraction.
- **Formats**: crease patterns in FOLD (JSON, Origami Simulator standard); rendered to SVG for display; tutorial steps as PNG images.
- **Non-goals**: commercial features/accounts/payments, multi-object or video input, physical (robot) folding, mobile apps, model training.
- **Definitions**: *tree* = object limbs connected at joints, each with a length; *box pleating* = creases constrained to a 45°/90° grid; *foldable* = flat-foldable (Maekawa/Kawasaki conditions) AND foldable in 3D simulation without self-intersection; *failure* = a defined halting condition reported to the user, never broken output.

## Architecture

```
browser (TypeScript)
  └─ React app: Upload → Pipeline status → Crease SVG + 3D simulator → Tutorial viewer
        ├─ Three.js folding simulator (FOLD import, fold ops, layer ordering, self-intersection guard)
        └─ REST calls to backend
backend (Python, FastAPI)
  ├─ /recognize      → pretrained segmentation+skeleton → limb tree → integer proportions
  ├─ /generate-crease→ grid packing (box pleating) → FOLD + SVG  + flat-foldability check
  ├─ /propose-fold   → AI/heuristic fold-topology proposal (mountain/valley + layer order)
  └─ /tutorial       → folding history → numbered steps manifest + PNGs (headless render)
shared artifacts
  ├─ validation/     → ~15 photos + expected tree YAML + expected outcome (success/failure)
  └─ strategies/     → curated folding-strategy library (JSON: limb shape → fold recipe)
```

Suggested repo layout:

```
origami-proj/
  backend/            # FastAPI app, recognition, generator, tutorial renderer, tests
  frontend/           # React + Three.js app, simulator, tutorial viewer, tests
  strategies/         # folding strategy library (curated JSON)
  validation/         # validation photos + expected outcomes
  docs/               # SDD, research notes (box pleating, FOLD, foldability)
```

## API Contract (v1)

- `POST /api/tutorial` — multipart upload of one photo.
  - `200 {status:"ok", tree, creasePatternUrl, tutorialSteps:[{index, imageUrl, instruction, mountain|valley, landmarks}]}`
  - `200 {status:"failure", code, message, remedy}` for defined halting conditions
  - `422` for malformed input; `413` for files > 20 MB.
- `POST /api/propose-fold` — `{creasePattern, currentState, targetHints}` → `{fold:{line, direction, layerOrder}}` or `{status:"no-proposal"}`. Used by the interactive simulator.
- `GET /api/crease/{id}.fold` / `GET /api/crease/{id}.svg` — generated artifacts.
- Status codes are stable and machine-readable; failure messages are user-facing and non-technical.

## UI Behavior

1. **Upload screen**: drag-and-drop; immediate validation (image, size, single object preview); clear error card for rejected inputs.
2. **Pipeline progress**: step indicators (Recognize → Assign → Generate → Simulate → Tutorial) with per-step status and estimated time; cancel allowed.
3. **Result view**: crease pattern as SVG (zoomable, grid overlay on/off) side by side with the 3D simulator; user can fold/unfold manually; AI proposals appear as highlighted next-fold suggestions with accept/reject.
4. **Tutorial viewer**: numbered steps, each with rendered PNG, mountain/valley indicator, landmark markers, and a one-line instruction; progress bar; "next fold" preview in the 3D view.
5. **Failure screen**: shows `code`, a plain-language `message`, and a `remedy` (e.g., "take a photo with less background clutter").

## Milestones

Milestones are ordered by risk retirement and value-per-effort, not by draft numbering. M0–M2 retire the two hardest risks (generation + simulation); M4 (photo recognition) is deliberately later because pretrained models make it lower risk and it is not needed for the first usable slice.

### M0 — Foundations (before any feature work)

- [ ] Initialize monorepo (backend/ + frontend/ + strategies/ + validation/ + docs/) with README, `.gitignore`, license for reused code.
- [ ] Add FOLD read/write library in Python with roundtrip tests; pin the FOLD spec (Origami Simulator JSON).
- [ ] Verify licenses of planned dependencies (Origami Simulator core is MIT — confirm; pretrained vision model licenses — confirm) and record in `docs/`.
- [ ] Set up CI: lint + unit tests on backend and frontend.
- [ ] Create `validation/` skeleton: 15 photo slots across animals, plants, simple objects; YAML expected-outcome format; collect the first 5 photos.
- **Done when**: repo builds, FOLD roundtrip tests pass, CI green, license review recorded.

### M1 — Box-pleating crease pattern generator (Goal 2 core)

- [ ] Implement integer limb-tree → grid crease pattern via grid packing (start greedy: largest limb first, 64×64 grid cap; local improvement passes).
- [ ] Round and normalize limb proportions to whole grid units; reject trees exceeding grid capacity with `TREE_TOO_COMPLEX`.
- [ ] Implement flat-foldability checker (Maekawa: mountain − valley = ±2 at each interior vertex; Kawasaki: alternating angle sums = 180°) and apply it to every generated pattern.
- [ ] Add random-restart + local search to escape poor assignments; hard time budget (default 5 min, tunable) → `NO_ASSIGNMENT_WITHIN_BUDGET`.
- [ ] Export FOLD + SVG (grid overlay); keep `propose-fold` as a pluggable interface — v1 ships deterministic heuristics, AI can be swapped in later without API change.
- **Time-box note**: this is the highest research risk. Cap work at 2 weeks of exploration; if grid packing for arbitrary trees stalls, freeze v1 scope to trees with ≤ 8 limbs and document the restriction.
- **Done when**: for ≤ 8-limb trees, patterns are flat-foldable, exported, and the validation sample's expected trees are covered.

### M2 — Folding simulator (Goal 4)

- [ ] Port/adapt Origami Simulator core folding algorithm to the frontend (FOLD in, folded state out).
- [ ] Implement fold operations (mountain/valley, partial folds) and layer ordering; record every fold into a fold-history log.
- [ ] Implement self-intersection guard: reject fold steps that cause facet intersections; report to user instead of corrupting state.
- [ ] Build the React UI: 3D viewer, grid overlay, undo/redo, manual fold, "suggest next fold" (calls `/api/propose-fold`).
- [ ] Enforce invariant: paper must never self-intersect at any time (unit + golden tests on known fold sequences).
- **Done when**: golden test set (cone, box, flat fold) folds without self-intersection; history log replays exactly; UI usable in browser.

### M3 — Folding strategy library (Goal 3)

- [ ] Define strategy schema: `{limbShape: cylinder|cone|box|flat|…, foldRecipe: [fold ops], applicable grid sizes}`.
- [ ] Curate initial ~15 strategies with hand-verified fold recipes; validate each in the simulator from M2.
- [ ] Add strategy lookup: given a limb from the tree, pick a matching strategy; record coverage gaps as `STRATEGY_UNCOVERED` (non-halting warning in v1).
- **Done when**: ≥ 15 curated strategies, each verified foldable in simulator; lookup unit-tested.

### M4 — Photo recognition (Goal 1)

- [ ] Integrate pretrained segmentation + skeleton/limb extraction; build post-processing: object mask → limb graph → lengths.
- [ ] Implement input checks: no object → `NO_OBJECT`; multiple objects → `MULTIPLE_OBJECTS`; longest side < 512 px → `LOW_RESOLUTION`.
- [ ] Round limb lengths to whole units; export limb shapes/textures for end-design hints.
- [ ] Golden-test recognition on the collected validation photos; record per-category accuracy.
- **Done when**: 15-photo validation set fully labeled; recognition pipeline runs end-to-end in backend; expected outcomes recorded.

### M5 — AI-driven folding workflow (Goal 5)

- [ ] Loop: current folded state vs target (from tree) → measure resemblance (silhouette IoU + limb landmark distance) → propose next fold → simulate → verify no self-intersection.
- [ ] Termination: stop on improvement < threshold, or step budget (default 50 folds, tunable); plateau → `RESEMBLANCE_PLATEAU` failure with explanation.
- [ ] Wire `/api/propose-fold` to the loop; keep heuristic v1, AI pluggable.
- **Done when**: on a test subset of validation photos, the loop terminates within budget and reaches the best attainable resemblance; failures are reported, not silent.

### M6 — Tutorial generation (Goal 6)

- [ ] Convert fold history into numbered steps; deduplicate/reorder noisy steps; cap at a readable count.
- [ ] Render each step as PNG (headless render of simulator state) with mountain/valley marker, landmarks, and one-line instruction written for non-experts.
- [ ] Emit tutorial manifest (JSON) + image bundle; validate manifest completeness in tests.
- **Done when**: golden histories produce complete, ordered tutorials; a non-expert can follow 3 generated tutorials to a recognizable result (spot-check protocol).

### M7 — Integration, validation run, polish (all goals)

- [ ] Wire the full pipeline in `/api/tutorial`; failure codes mapped end-to-end (see Failure Handling).
- [ ] Run the acceptance protocol on the 15-photo validation set; log per-photo outcome vs expected.
- [ ] Fix all halting conditions to produce `{status:"failure", code, message, remedy}` — no 500s, no partial tutorials.
- [ ] UI polish: upload → progress → result → tutorial flows; reduced-motion support; mobile-friendly layout (view-only).
- **Done when**: acceptance criteria below are met.

## Failure Handling (implementation mapping)

| Condition | Code | Enforced in |
|---|---|---|
| No object / multiple objects / low resolution | `NO_OBJECT`, `MULTIPLE_OBJECTS`, `LOW_RESOLUTION` | M4 |
| Tree too complex for paper/grid | `TREE_TOO_COMPLEX` | M1 |
| No valid assignment within search budget (5 min default) | `NO_ASSIGNMENT_WITHIN_BUDGET` | M1 |
| Shape not representable by box pleating (mathematically impossible) | `NOT_BOX_PLEATABLE` | M1/M5 |
| Resemblance plateau before target reached | `RESEMBLANCE_PLATEAU` | M5 |
| No strategy matches a limb (warning, non-halting) | `STRATEGY_UNCOVERED` | M3 |

All codes produce a user-facing message + remedy. Integration test asserts each condition.

## Testing & Acceptance

- **Unit tests**: FOLD roundtrip; Maekawa/Kawasaki checker (valid + invalid patterns); integer rounding; input rejection rules; strategy lookup; resemblance metric on synthetic cases.
- **Simulator golden tests**: known sequences (cone, box, flat) fold without self-intersection; fold-history replay equals the recorded sequence.
- **Integration tests**: headless run of the full pipeline per validation photo; assert success or expected failure code (no 500s).
- **Acceptance criteria (from draft)**, measured in M7:
  - Validation set: ~15 photos across animals, plants, simple objects.
  - ≥ 80% (12/15) produce a tutorial whose crease pattern is verified foldable in the simulator.
  - Spot check: one non-expert folds 3 generated tutorials to a recognizable result.
  - Every failure terminates with a clear explanation instead of broken output.

## Sequencing & Prioritization

**Order rationale (value-per-effort, risk first):** M1 and M2 retire the two make-or-break risks (generation + simulation) before building anything on top; M3 is cheap and validates simulator use; M4 is low risk (pretrained models) and can slip without blocking M1–M3; M5–M6 only make sense after 1–4; M7 is the acceptance gate.

**First release (MVP) — MoSCoW:**
- **Must**: M0, M1 (≤ 8 limbs), M2, minimal tutorial path from a known tree, failure codes, validation subset.
- **Should**: M3 full ~15 strategies, M4 photo recognition, M5 basic loop.
- **Could**: M7 polish, animated 3D previews, step-deduplication improvements.
- **Won't (this release)**: multi-object/video input, accounts, robot folding, mobile apps, trained AI models, `propose-fold` AI beyond heuristics.

**Explicitly deferred**: Goal 7 extensions (per-object-class strategy selection, video input, animated previews); tuning of search/step budget defaults until first prototype; strategy library beyond ~15 patterns; any model training.
